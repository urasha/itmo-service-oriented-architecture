### Расхождения и неизвестные, которые нельзя скрыть

- В исходном Java-классе ЛР1 **нет `price`**, хотя агентство должно сравнивать стоимость. В обоих YAML `price` уже введён и обязателен: полная цена в рублях, минимум 0.01, шаг 0.01. Реализовать это решение; не придумывать расчёт цены по площади. Отметить расхождение в README для защиты.
- `PATCH` и специальные ответы `303` добавлены спецификацией ЛР1; в ЛР2 они обязательны, хотя исходное условие их не перечисляет.
- `404` в YAML описан преимущественно как отсутствие коллекции, даже у операций над отдельной квартирой. Принятое толкование: неизвестный ID → `404 Error`; коллекция существует с запуска, пустая коллекция → `[]`, `count=0` либо `204` для экстремумов. Не создавать механизм удаления/создания коллекций ради формулировки. Уточнить описания `404` при реализации, сохранив статусы и схемы.
- В YAML нет `servers`: Try it out по умолчанию использует origin документации, что неверно для агентства на другом порту. Добавить адреса через конфигурацию опубликованной документации, без фиксации личных портов в исходных YAML.
- Не заданы долговременное хранение, авторизация, пользователи, поиск подстрок, диапазонные фильтры, максимальный размер страницы и максимальные длины строк. Не добавлять их как требования.
- Неизвестны доступные JDK/ОС/архитектура Helios, разрешённые порты, квоты и уже установленные серверы. Это **блокер подтверждения развёртывания выбранного стека**, а не анализа API. Доступ к Helios не проверялся; успешный запуск на нём не заявляется.

## 2. Зафиксированный контракт

### Операции

| Метод и путь | Успешный результат | Существенные особенности |
| --- | --- | --- |
| `GET /flats` | `200`, массив, `X-Total-Count` | Фильтр → сортировка → страница; пустая/запредельная страница `[]`. |
| `POST /flats?flat=...` | `201`, `Location` | Сервер назначает ID и дату; тело ответа не обещано, клиент получает созданную квартиру отдельным GET. |
| `GET /flats/{id}` | `200 Flat` | Положительный int64; неизвестный ID → 404. |
| `PUT /flats/{id}?flat=...` | `200 Flat` | Полная замена пользовательских полей; ID и дата сохраняются; необязательные пропуски → null. |
| `PATCH /flats/{id}?flat=...` | `200 Flat` | Только переданные поля, включая частичные вложенные объекты; различать пропуск и null. |
| `DELETE /flats/{id}` | `204`, без тела | Повторное удаление отсутствующего объекта → 404. |
| `GET /flats/min-creation-date` | `200 Flat` / `204` | Любой объект с минимальной датой; 204 при пустой коллекции. |
| `GET /flats/max-new` | `200 Flat` / `204` | true больше false; 204 при пустой коллекции. |
| `GET /flats/count-by-transport?transport=...` | `200 {"count":N}` | JSON-строка `"FEW"`, `"NONE"`, `"LITTLE"`, `"ENOUGH"` либо JSON null. |
| `GET /agency/get-cheapest/{id1}/{id2}` | `200 Flat` / `303` | Минимальная цена; при равенстве цен первая; при одинаковых ID — 303 на первый сервис. |
| `GET /agency/get-most-expensive/{id1}/{id2}/{id3}` | `200 Flat` / `303` | Максимальная цена; при равенстве первая из максимальных; 303 только когда все три ID одинаковы. |

Полный перечень допустимых ошибок брать из YAML: первый сервис — `400/404/414/422` в соответствующих операциях; агентство — `400/404/502/504`. Все прикладные ошибки имеют ровно `{timestamp, message}`; timestamp в UTC с `Z`. `204` и `303` не требуют JSON-тела. Статические пути первого сервиса должны разрешаться раньше шаблона `{id}`.

### Разбор и валидация

- POST/PUT/PATCH передают **URL-encoded JSON в query-параметре `flat`**, а не request body. Аналогично устроен `filter`; счётчик получает JSON-значение `transport`. Не переносить входные данные в тело ради удобства фреймворка.
- Сначала строго разобрать JSON и структуру: неверный тип, неизвестное поле, недостающее обязательное поле, запрещённые `id`/`creationDate`, пустой patch/вложенный patch → 400. Ошибки ограничений допустимо сформированного объекта (например, area=0, rooms=9, отрицательная цена) → 422 для операций изменения. Некорректные параметры выборки/ID → 400. Не использовать неявные преобразования строк в числа и null в 0/false.
- Flat: `id > 0`, автоматически и уникально; `name` непустая строка; `coordinates` и оба числа обязательны; дата автоматически; `area > 0`; `numberOfRooms` 1..8; обязательный boolean `new`; обязательные `view` и `house`. Поле Java назвать `isNew` с JSON-именем `new`. Ввод даты не принимать.
- `view`: YARD, NORMAL, GOOD, TERRIBLE. `transport`: FEW, NONE, LITTLE, ENOUGH либо null. **NONE и null различаются.** В ответе Flat поле transport присутствует даже при null.
- House: name обязателен, но пустая строка разрешена схемой; numberOfFloors обязателен и >0. year, numberOfFlatsOnFloor, numberOfLifts могут отсутствовать/null; при наличии >0. Не превращать все поля дома в обязательные.
- `price` хранить и сравнивать как `BigDecimal`, без округления входа. Проверять математическую кратность 0.01, а не просто число знаков записи (1.000 допустимо). Не вводить неописанный верхний предел стоимости.
- Для PATCH использовать дерево JSON с проверкой наличия ключей; после слияния валидировать целый объект. Ошибка не должна частично изменять запись.
- В JSON-числах координат не принимать NaN/Infinity; контролировать переполнение float/double/int32/int64. Дата `LocalDate`, ошибки времени — `Instant`; серверную зону для даты документировать (проектное решение: Europe/Moscow), в тестах подменять Clock.

### Фильтры, сортировка, страницы

- `page` и `size` — int32 >=1, по умолчанию 1 и 20. При расчёте смещения использовать long, чтобы умножение не переполняло int. Не добавлять скрытый предел size.
- `filter` — частичный FlatFilter, точное равенство, все условия объединяются AND; вложенные условия задаются объектами. Пропуск не ограничивает выборку; null выбирает null только в nullable-полях; `{}` и пустые вложенные фильтры ничего не ограничивают. Не подменять это строковым contains или OR.
- Поддержать все поля схемы: id, name, coordinates и x/y, creationDate, area, price, numberOfRooms, new, view, transport, house и name/year/numberOfFloors/numberOfFlatsOnFloor/numberOfLifts. Фильтры целых объектов означают комбинацию их вложенных условий.
- Сортировки повторяются: `sort=area:asc&sort=name:desc`, порядок параметров задаёт приоритет. Повтор одного поля даже с другим направлением → 400. Остальные query-параметры списка не могут повторяться.
- По умолчанию `id:asc`; дописать id:asc последним ключом, если id не указан. Строки — Unicode, с учётом регистра (для символов за пределами BMP проверить порядок кодовых точек); boolean false < true; enum в порядке объявления. null всегда последним, в том числе при desc: не делать reverse всего nullsLast-компаратора.
- Сортировка coordinates разворачивается в x/y; house — name/year/numberOfFloors/numberOfFlatsOnFloor/numberOfLifts. Направление применяется к каждому ключу. Сортировка объекта и его дочернего пути совместно не запрещена YAML; не считать это повтором разных имён полей.
- `X-Total-Count` считать после фильтрации, до пагинации, на том же согласованном снимке данных.

### Агентство

Агентство не хранит коллекцию: выполняет HTTPS GET первого сервиса, проверяет его статус и содержимое, сравнивает цены. Два/три последовательных вызова достаточны; параллелизм, кэш и повторные попытки не нужны. Частично повторяющиеся ID допустимы; порядок аргументов сохраняется для ничьих.

Ошибки: некорректный собственный ID → 400; upstream 404 → 404; timeout → 504; отказ подключения, ошибка TLS, прочие ошибочные статусы, неожиданный статус без Flat или некорректный JSON/Flat → 502. Не возвращать неполный результат при ошибке одного GET. Задать конечные connect/request timeout (проектные defaults: 3/5 секунд; суммарное ожидание трёх последовательных запросов учитывать в UI).

Для одинаковых ID валидировать ID и вернуть 303 без обязательного запроса upstream. `Location` — **абсолютный публичный HTTPS URL первого сервиса**, поскольку относительный `/flats/1` на origin Payara ведёт не туда. Формат `uri-reference` допускает абсолютный адрес. Внутренний адрес серверного вызова и публичный адрес редиректа задаются отдельно; не брать host из непроверенного заголовка запроса.

## 3. Минимальная архитектура и стек

```text
Браузер
  ├─ HTTPS → Jetty : FLATS_HTTPS_PORT
  │            ├─ /app/       пользовательский клиент (HTML/CSS/JS)
  │            ├─ /docs/      существующий Swagger UI + YAML
  │            └─ /flats...  Spring MVC, коллекция в памяти
  └─ HTTPS → Payara : AGENCY_HTTPS_PORT
               └─ /agency... JAX-RS
                      └─ HTTPS → Jetty /flats/{id}
```

Два отдельных процесса серверов, два WAR и один небольшой общий JAR; статический клиент включается в WAR первого сервиса. Отдельный процесс фронтенда/веб-сервера не нужен. Все три компонента таким образом размещаются на Helios. Порты на схеме — переменные, а не обещанные значения.

| Часть | Решение |
| --- | --- |
| Java / сборка | JDK 17, Maven 3.9.x, `maven.compiler.release=17`, UTF-8. Сборка локально, на Helios переносить готовые WAR. |
| Первый сервис | Spring Framework **6.2.x**, `spring-webmvc`, обычный WAR под **внешним Jetty 12.0.x**, окружение **ee10**, Servlet 6.0 provided. Spring Boot и встроенный контейнер не нужны. |
| Второй сервис | **Payara Server Community 6.x**, Jakarta EE 10, Jakarta REST/JAX-RS 3.1, `jakarta.jakartaee-api:10.0.0` со scope provided. Реализацию JAX-RS предоставляет Payara. |
| JSON | Jackson **2.x** + jsr310; один набор версий через BOM, общий настроенный codec. Spring использует его message converter. Агентство читает/пишет JSON через codec и JAX-RS String entity с application/json: не подключать второй Jersey/Jackson provider поверх Payara. |
| REST-клиент агентства | Стандартный `java.net.http.HttpClient`, отдельный SSLContext/truststore, конечные таймауты, без автоматического следования upstream-редиректам. |
| Хранилище | Коллекция в памяти первого сервиса, монотонный счётчик ID и короткие synchronized-операции. Изменение атомарно; чтение списка работает с копией снимка. После рестарта коллекция и счётчик сбрасываются — это явно документируется. |
| UI | HTML, CSS, JavaScript ES modules, fetch; без Node на сервере, SPA-фреймворка и отдельной сборочной цепочки. |
| Проверки | JUnit 5, Spring Test/MockMvc; black-box интеграционные тесты через JDK HttpClient против настоящих контейнеров. OpenAPI parser только в test scope для проверки контрактов. |

Совместимость выбранных семейств подтверждается матрицами: [Spring: JDK 17 и Jakarta EE 10 для 6.2](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-Versions), [Jetty 12.0: Java 17 и EE10](https://jetty.org/docs/jetty/12/index.html), [развёртывание ee10 WAR](https://jetty.org/docs/jetty/12/operations-guide/deploy/index.html), [Payara 6: поддерживаемые JDK](https://docs.payara.fish/community/docs/6.2025.10/General%20Info/Supported%20Platforms.html), [сертификация Payara/Jakarta EE 10](https://jakarta.ee/compatibility/certification/10/). Это вывод о совместимости API, а не результат запуска на Helios.

Версии выше — линии совместимости. В шаге 0 зафиксировать конкретные доступные patch-релизы в POM/`deploy/versions.env` после пробного запуска на целевой JVM; не оставлять `LATEST`, диапазоны или SNAPSHOT. Payara 6.2025.10 — документированный кандидат для проверки, не требование задания. На дату анализа открытая поддержка Spring 6.2 уже завершена (июнь 2026, см. матрицу Spring); это компромисс учебного EE10-стека, а не рекомендация для промышленной эксплуатации. Не смешивать Spring 7/Servlet 6.1 с ee10 при случайном обновлении. Если политика окружения запрещает эти версии, сначала пересогласовать стек, а не незаметно менять поколения зависимостей.

**Граница минимальности:** никаких БД/JPA, брокеров, discovery, gateway, Docker/Kubernetes, OAuth, общего runtime-хранилища или отдельного backend клиента. Долговременное хранение добавлять только при появлении прямого требования. Общий JAR содержит лишь модель, JSON и проверку модели; зависимости сервисов друг от друга запрещены.

## 5. HTTPS, браузер и Helios

### TLS и адреса

1. Создать разные серверные ключи/самоподписанные сертификаты Jetty и Payara. Использовать keytool, SAN для фактических DNS-имён/IP, которыми пользуются браузер и агентство; для локальной проверки включить localhost и 127.0.0.1. CN без SAN недостаточен.
2. Jetty: отдельные JETTY_HOME и JETTY_BASE; включить ee10-deploy и ssl/https, задать keystore и выделенный TLS-порт. **Не включать http**. Базовая механика описана в [официальном руководстве Jetty TLS](https://jetty.org/docs/jetty/12/operations-guide/protocols/index.html).
3. Payara: отдельный пользовательский domain, HTTPS listener с нужным alias сертификата, HTTP listener отключён. Проверить реальные пути свойств через asadmin get/list для зафиксированного релиза; шаблон не должен предполагать, что имя listener равно имени protocol. Управление HTTP/TLS описано в [Payara Administering HTTP Connectivity](https://docs.payara.fish/community/docs/6.2025.4/Technical%20Documentation/Payara%20Server%20Documentation/General%20Administration/Administering%20HTTP%20Connectivity.html).
4. Импортировать публичный сертификат Jetty в отдельный truststore клиента агентства. SSLContext назначить только FlatsClient; не заменять глобальный truststore JVM/домена. Сохранить hostname verification, не применять trust-all или `curl -k` как критерий успешной проверки.
5. Не заменять Payara keystore целиком: сохранить служебные alias домена; импортировать свой ключ и назначить alias именно HTTPS-протоколу приложения. Тип/пароли штатного keystore проверять у выбранной версии, не считать его автоматически PKCS12.
6. Браузер должен доверять **обоим** сертификатам. Инструкция пользователю: импорт сертификатов либо явное принятие исключения для каждого origin, если браузер допускает. JavaScript не умеет отключать проверку сертификатов.
7. Разделить `FLATS_INTERNAL_BASE_URL` (для Payara), `FLATS_PUBLIC_BASE_URL` (редиректы/документация), `AGENCY_PUBLIC_BASE_URL` (браузер). Только HTTPS. При SSH-туннелях публичные адреса могут быть localhost, внутренний адрес остаётся доступным самому Helios. SAN и CORS должны соответствовать выбранному режиму.
8. HTTP-порты приложений закрыты/не слушают; редирект HTTP→HTTPS не заменяет запрет HTTP. Отдельно проверить, что ни default web module, ни другой listener Payara не публикуют WAR по HTTP. Администрирование Payara ограничить loopback/SSH; удалённый admin при необходимости только secure admin.

### CORS и клиент

- Клиент обслуживается Jetty: вызовы flats идут на тот же origin, к Payara — другой origin. На агентстве разрешить конкретный origin клиента и GET/OPTIONS; без credentials и wildcard. OPTIONS — инфраструктурная поддержка, не новая бизнес-операция.
- При автоматическом следовании fetch за 303 запрос может прийти к Jetty с изменившимся Origin, включая `null` при переходе между origin. API публичный без cookies: для **GET `/flats/**`** допустимо `Access-Control-Allow-Origin: *`, без credentials, с expose `X-Total-Count, Location`; это позволяет чтение результата редиректа. Методы изменения не открывать произвольным origin. Проверить цепочку реальным браузером, включая CORS на ошибках.
- `fetch` обычно скрывает промежуточный статус 303 после следования, а `redirect: manual` не даёт переносимого доступа к cross-origin Location. UI использует автоматический follow и показывает итоговую квартиру; сам 303 проверяется отдельным HTTP-тестом без follow.
- `config.js` и runtime-конфигурация Swagger содержат только публичные URL, без паролей. Генерировать/подставлять их при подготовке WAR/deployment; internal hostname не отправлять клиенту. Для обоих Swagger-документов задать соответствующий `servers` через загруженные JS объекты спецификаций.
- UI: таблица с раскрытием всех полей; создание; получение по ID; полная замена; частичное обновление с явным выбором изменяемых полей; удаление; оба экстремума; счётчик с отдельными вариантами null/NONE; две формы агентства. Для PATCH различать «не менять», «задать», «null» в nullable-полях.
- Конструктор фильтров для всех полей и nullable-значений; повторяемые строки сортировки с выбором направления/приоритета; page/size и общее количество. Изменение фильтров возвращает страницу 1. Пустые выборки и 204 отображаются текстом, не как ошибка JSON.parse.
- У числовых полей int64 и price возможна потеря точности через JS Number. В `json-numbers.js` предусмотреть lossless-разбор/сериализацию числовых лексем (не заменять цифры regexp внутри JSON); хранить ввод ID/целых/цены строками и отправлять как JSON numbers. Допустимо взять маленький локально поставляемый lossless JSON codec с лицензией вместо самостоятельного парсера; это не требует Node на Helios. Проверки: ID/area > 2^53, точные копейки, float/double в экспоненциальной записи. Нельзя сужать API до Number.MAX_SAFE_INTEGER или переводить серверные числа в JSON-строки.
- Общий fetch wrapper различает статусную ошибку Error, пустой ответ, сетевой/TLS/CORS сбой и таймаут. При непрозрачной браузерной ошибке не утверждать конкретную причину. HTTP-код и message показывать пользователю; сообщение выводить через textContent. После ошибки изменения сохранять введённые поля.

### Подготовка Helios

Предварительная проверка под своей учётной записью: `uname -a`, `uname -m`, `java -version`, пути доступных JDK, доступность свободных разрешённых портов, `ulimit -a`, квота диска, разрешения каталогов, сетевой доступ между двумя listener и из браузера. Записать результаты в `docs/HELIOS_DEPLOYMENT.md`; не подставлять чужие порты/логины из примеров.

Если ОС Solaris/illumos/SunOS, не считать Linux-бинарники JDK совместимыми. В документации проверенного Payara 6 Solaris не перечислен; нужна проба на фактической JVM/ОС. Если подходящая JDK 17+ недоступна, это стоп-фактор выбранного стека до уточнения среды; не переписывать незаметно на Spring 5/Payara 5/`javax.*`.

Развёртывание без root: каталоги дистрибутивов и конфигурации в домашнем каталоге пользователя, незанятые высокие порты, собственный domain Payara. Учесть не только HTTPS/admin, но и остальные listener/служебные порты Payara; ненужные отключить либо назначить уникальные. Не предполагать Docker, systemd, GNU-only утилиты или доступ Maven Central с Helios. Собирать локально; переносить WAR, серверные дистрибутивы и конфигурацию при необходимости.

Скрипты shell с LF/UTF-8, совместимые с фактическим `/bin/sh`; start/stop используют собственные PID и проверяют процесс, не `pkill java`. Процессы переживают завершение SSH-сессии (`nohup`/штатный daemon start), логи разделены. Память Jetty/Payara задаётся отдельно и проверяется в пределах квоты. Ключи/пароли/локальные env не коммитить, права каталогов/файлов ограничить; в документацию включать только публичные сертификаты/отпечатки и имена параметров.

Минимальный `env.example`: пути JAVA_HOME/JETTY_HOME/JETTY_BASE/PAYARA_HOME/PAYARA_DOMAIN_DIR, имя домена, bind address, порты приложений и admin, три base URL, CORS origin, пути keystore/truststore, alias, источник паролей, heap и таймауты. Секреты задаются локальными защищёнными файлами, не в клиентском config.js.

## 7. Риски и обязательные проверки

| Риск | Решение и проверка |
| --- | --- |
| JVM/ОС Helios не подходят | Самый ранний инфраструктурный gate: фактическая ОС/архитектура/JDK и пробный запуск. JDK Windows/Linux не переносить на SunOS; не считать наличие java доказательством нужной версии. |
| `javax`/`jakarta`, версии Servlet | Выбран только Jakarta EE10: Spring 6.2, Jetty ee10, Payara 6. Проверить dependency tree, содержимое WAR и загрузку настоящими контейнерами. |
| Состояние поддержки библиотек | Spring 6.2 уже вне открытой поддержки; фиксировать patch-версии и учитывать правила учебного окружения. Совместимость не означает актуальную поддержку безопасности. |
| Jetty не разворачивает MVC WAR | Использовать внешний Jetty, ee10-deploy, и поддержку ServletContainerInitializer/annotations, если её требует WebInitializer; проверить DispatcherServlet. При необходимости явный web.xml вместо предположений об автоконфигурации. |
| Payara конфликты библиотек/контекстов | API provided, JAX-RS от сервера, без собственного Jersey/RESTEasy provider. Context `/` и ApplicationPath `/agency` проверяются запросом к точному URL. |
| Payara занимает чужие порты/квоту памяти | Собственный domain, уникальные служебные порты, ограничение heap, минимум нужных сервисов, журналы ошибок запуска. |
| HTTPS включён, но HTTP остался | Инспекция listeners и негативные сетевые пробы каждого опубликованного приложения. На HTTP не должно быть данных API/клиента. |
| Сертификат доверен, hostname неверен | SAN для internal/public/туннельных адресов; проверять оба TLS-перехода, отрицательную проверку hostname и срок действия. |
| 303/CORS/сертификаты ломают браузер | Абсолютный публичный Location, доверие обоим origin, CORS на GET/ошибках, проверка follow в настоящем браузере; не полагаться только на curl. |
| JSON в URL, длинная кириллица | URLSearchParams/корректное процентное кодирование; проверять `+`, `&`, `#`, кавычки и Unicode. Согласовать предельную длину URI как deployment-параметр, не вводить ограничения схемы строк. |
| `414 Error` против раннего отказа Jetty | Контейнер может отклонить request line/headers до MVC и вернуть собственный статус/HTML. У Jetty документирован requestHeaderSize ([модули](https://jetty.org/docs/jetty/12/operations-guide/modules/standard.html)). На шаге 2/3 испытать границу и запросы за ней; согласовать app/container limits и при необходимости добавить Jetty-level error handling. Один ControllerAdvice не доказывает соблюдение 414. Если валидный HTTP с длинным URI не получает договорённый 414 JSON, это открытый дефект соответствия, а не «тест прошёл». Повреждённые TLS/HTTP-пакеты JSON-ответа не гарантируют. |
| Точность цены/int64, null и coercion | BigDecimal/long на сервере, lossless числа в UI, строгий JSON decoder и тесты на больших числах/0/false/null. |
| Потеря изменений/расхождение total со страницей | Атомарный merge/validate/store; согласованный снимок на чтение. DTO не отдаёт наружу изменяемые внутренние объекты. |
| Сброс коллекции после рестарта | Допустимое выбранное поведение при отсутствии требования persistence; явно написать в README и демонстрировать тестовый набор через API. |
| Полная проверка только MockMvc | MockMvc не проверяет TLS, лимиты HTTP, CORS браузера и Payara deployment. Завершать реальными HTTPS black-box и ручными браузерными проверками. |
